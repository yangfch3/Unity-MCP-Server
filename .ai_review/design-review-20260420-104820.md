## 2. 自由评审意见

1. **Correctness Properties 章节是一个亮点**。5 条形式化属性覆盖了输出捕获、状态恢复、异常处理、安全门控和响应格式，为 Property-Based Testing 提供了清晰的验证依据。Property 引用的 "Requirements X.X" 编号在文档中没有对应的 Requirements 章节，但考虑到这是内部设计文档（非外部需求规格书），这些编号更像是内部追踪标记，可以接受。

2. **`_executionLock` 在 `Execute()` 中的作用域需注意**。伪代码显示 `lock` 包裹了从编译到执行的整个流程，这意味着如果一个调用超时（10s），第二个并发调用需要等待第一个完全退出 lock 后才能开始。最坏情况下第二个调用可能在 `MainThreadQueue` 的 10s 超时内等不到锁而被丢弃。这在 MVP 场景下是可接受的（并发调用不太可能），但值得在文档中注明。

3. **Error Handling 表的 `Toggle OFF` 行与 Response Builder 描述不完全一致**。Error Handling 表写的是 `Return ToolResult.Error(...)`，而 Property 5 声明 "for any invocation...the returned text SHALL be valid JSON containing exactly three keys"。Toggle OFF 时返回的是 `ToolResult.Error` 的纯文本，不含 JSON 三字段格式。Property 5 中应排除 Toggle OFF 场景，或者 Toggle OFF 也返回三字段 JSON。

## 3. 改进建议

### 🟡 建议改进（推荐修改）

1. **时序图中 `await` 改为 `block/join`** — 第 47 行 `Tool->>Tool: await with 10s timeout` 建议改为 `Tool->>Tool: thread.Join(10s) [blocks main thread]`，与伪代码和 Thread Model Decision 段落保持一致。

2. **Property 5 与 Toggle OFF 场景的矛盾** — Property 5 声称 "For any invocation" 返回三字段 JSON，但 Toggle OFF 返回 `ToolResult.Error(纯文本)`。建议二选一：(a) Property 5 排除 Toggle OFF 场景（`For any invocation where toggle is ON`）；(b) Toggle OFF 也返回三字段 JSON（通过 `ToolResult.Success` 包裹 `success: false`）。推荐方案 (a)，因为 Toggle OFF 本质是"tool 不可用"，用 `ToolResult.Error` 语义更正确。

3. **补充编译阶段耗时预期** — 在 Compilation Logic 或 Thread Model Decision 中加一句：编译阶段在主线程同步执行，预期耗时 < 1s（小代码片段 + 内存编译），但引用的程序集数量可能影响耗时。如果未来发现编译耗时过长，可考虑将编译也移到后台线程。

### 🟢 锦上添花（可选优化）

1. **`_executionLock` 最坏等待时间注释** — 在伪代码或 Key points 中补充一句：并发调用时，后续调用需等待前一个完成（含超时），最坏等待约 10s + 编译时间。
